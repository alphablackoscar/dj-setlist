# app — セットリストを作る画面（Electron）

**音源にもネットワークにも触らない。** solver を子プロセスとして呼ぶだけ。

## 起動

**リポジトリ直下の `セットリストを作る.command`（Mac）/ `.bat`（Windows）をダブルクリック。**
初回だけ Electron（約 250MB）を自動で取ってくるので数分かかる。

```bash
# ターミナルから起動したいとき
cd packages/app && npm install && npm start
```

`.app` や Dock から Electron を直接起動すると、ログインシェルの PATH が読まれず
`node` が見つからない。**`.command` は Terminal.app 経由でログインシェルとして走る**ので
`~/.zprofile` などの PATH がそのまま効く。これが `.command` にしてある理由。

開いた黒い窓は閉じないこと（閉じるとアプリも終わる）。

## テスト

```bash
cd packages/app && npm test
```

**Electron を実際に起動して、実際にクリックする通しテスト**（`test/ui-smoke.js`）。
タブの切り替え / ここまで確定 / 変える と、その組み合わせを 24 項目確かめる。
2〜3 分かかる（solver を 8 回呼ぶため）。

画面を触ったら必ず走らせること。**目視では「案 C で変えると案 A だけになる」類の
不具合が素通りする**（実際に素通りした）。

## 開発は Mac、実際に使うのは Windows

| | |
|---|---|
| **Mac** | 画面を書く。features.db と collection.xml は git 経由で来ているので、音源なしで全部作れる |
| **Windows** | 実際に使う。**試聴**（音源がある）と **rekordbox への読み込み**があるため |

Electron は同じソースが両方で動くので、これは分岐ではない。git で pull して `npm start` するだけ。

`.exe` 化（electron-builder）は**今はやらない**。自分専用なら `npm start` で足りる。
設定が重いわりに得るものが「アイコンをダブルクリックできる」だけなので、欲しくなってから。

## 作りの約束

**solver を子プロセスとして今の CLI をそのまま呼ぶ。** 画面側に solver のロジックは 1 行も無い。

1. **CLI と画面の挙動が絶対にずれない**（同じものを呼んでいるので）
2. **ビルド工程が増えない**（solver は Node 24 が `.ts` をそのまま実行する。この長所を壊さない）
3. **solver が落ちても画面は生き残る**

3 案で 2.3 秒なので、プロセスを起動し直す分を足しても体感は変わらない。

**Electron 同梱の Node ではなくシステムの Node を呼ぶ**（Electron 33 の Node は 20 系で
TypeScript を直接実行できないため）。Mac / Windows どちらにも Node 24 がある。

```
画面 ──window.dj.solve(argv)──▶ preload ──IPC──▶ main.js ──spawn──▶ node cli.ts --json
                                                                        │
画面 ◀───────────────── JSON（案 3 つ・群の一覧・書き出し済みファイルの場所）
```

`--json` を付けると **標準出力が JSON 専用**になり、人向けの出力は標準エラーに回る。

## 画面

1 枚。左にオーダー、右にセットリスト。**切り替えない** —
実務は「案を見る → 条件を変える → また出す」を行ったり来たりするため。

**主役は行のボタンであって設定のつまみではない。** DJ が実際にやるのは頭から順に固めていくこと。

| ボタン | CLI | 何が起きるか |
|---|---|---|
| **ここまで確定** | `--drop <位置>` | その行から下だけを 3 案作り直す。**上は動かない**（緑で示す） |
| **替える** | `--swap <位置>` | その 1 曲だけ差し替える。前後は動かさない |

選ぶ単位は **音の群れ 8 個**（`config/sound_groups.json`）。
39 個のジャンルではなくこちらを使うのは、**ジャンル欄が空の 1331 曲が選択から漏れないため**。

各行に出すのは **曲名 / アーティスト / BPM / キー / 音の群れ** だけ。
「なぜこの曲か」は出さない（見れば分かる）。BPM とキーが縦に追えることを優先している。

## 試聴（▶）

**Windows でしか鳴らない**（音源は Windows から出さない約束）。Mac では
「この機械には音源がありません」と出る。

- **頭出しは解析が「その曲らしい」と判断した位置から**（`window_start`）。
  イントロから聞かせても曲の性格が分からないため
- mp3 / wav / m4a はそのまま流す（Range 対応で頭出しが速い）
- Chromium が鳴らせない形式（**aiff 90 曲**）は ffmpeg で mp3 に変換しながら流す。
  Windows には analyzer 用の ffmpeg が入っているのでそれを使う
- `djaudio://` という専用の口だけで配り、**solver が返した曲以外は配らない**
  （画面から任意のファイルを読めないようにするため）

## 書き出し

**`out/` は作業場。** 実行のたびにファイルが増えるので、7 日より古いものは自動で消す
（`config/weights.json` の `out_keep_days`）。

残したいセットは **「このセトリを書き出す」** で名前を付けて保存する。
`セトリ_2026-08-08_EDM_128BPM_13曲_案C.xml` のような名前が既定で入る。
rekordbox の「ファイル > 読み込み > コレクション XML を読み込み」で取り込む。
素の再生リスト（.m3u8）も隣に一緒に保存される。

## 曲を足したとき（「XML を読み込み」）

rekordbox で曲を足したあと、**画面だけで完結する**。ターミナルも AI も要らない。

1. rekordbox で「コレクションを XML に書き出し」
2. 画面左下の **「XML を読み込み」** でそのファイルを選ぶ
3. 3 つの工程が続けて走る。**どれも「済んだ曲は飛ばす」**ので、増えた分しか時間がかからない

| 工程 | 中身 | 時間 |
|---|---|---|
| 曲名やジャンルの更新 | `--refresh-meta`。あとから rekordbox でジャンルを埋めた分を反映 | 約 1 秒 |
| 増えた曲の解析 | 通常実行。`status='done'` 以外だけ | **1 曲 10.9 秒** |
| 曲の起伏 | `--envelope`。起伏を持っていない曲だけ | 1 曲 0.5 秒 |

**判断が要る所は無い。** ジャンルのテキストを捨てて音の群れに切り替えたので、
未知のジャンル名が来ても `canonical` が空になるだけで**音の群れは必ず付く**。
新しい曲が選曲から漏れない（`config/genre_map.json` の手当ては不要になった）。

- **群の作り直しも不要。** 中心点だけを保存して割り当ては毎回計算するので、足した曲は自動で入る
- 元の `data/collection.xml` は `.bak` として残す
- 途中で「やめる」を押しても壊れない。**1 曲ごとに DB へ書く**ので、次に押せば続きから
- **「ファイルが見つかりません」が毎回 15 曲出るが異常ではない。** rekordbox に登録だけ
  残って実ファイルが無い曲を毎回試すため。終了時のメッセージでその旨を明示している

**Mac に渡すには `data/features.db` の commit & push が別に要る**（画面からはできない）。

## まだ無いもの

- 曲数の直接指定、curve の切り替え、BPM 帯の手入力（今は箱の既定を使う）
- `--genres` によるテキストのジャンル選択（CLI 側にはある）
- 差し替えの候補を選ぶ画面（今は押すたびに 1 曲が自動で決まる）
- Mac への受け渡し（commit & push）のボタン
